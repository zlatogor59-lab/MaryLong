# Сервер приложения консультанта

Первый безопасный каркас по спецификации Obsidian. Реальные клиентские данные не используются.

## Локальный запуск

1. Скопировать `.env.example` в `.env` и заменить демонстрационные значения.
2. Запустить PostgreSQL 16+.
3. Выполнить `pnpm install`, `pnpm prisma:generate`, `pnpm prisma:migrate`.
4. Запустить `pnpm start:dev`.

После запуска web-интерфейс доступен на `http://localhost:3000/`. Вход использует OIDC Authorization Code + PKCE. Укажите `AUTH_CLIENT_ID` и redirect URI в `.env`; client secret для SPA не используется. Access token хранится только в памяти страницы.

При установленном Docker локальный PostgreSQL запускается командой `docker compose up -d postgres`. Конфигурация привязывает порт только к `127.0.0.1` и предназначена исключительно для синтетических данных.

Публичная проверка: `GET /api/v1/health`. Остальные маршруты закрыты глобальным guard.

## Границы текущего шага

- Созданы первые шесть таблиц и ограничения базы.
- Создана проверка OIDC JWT и прикладного отзыва сессии.
- `users` подключён через Prisma; `/me` возвращает только безопасный DTO.
- Политики AUTH-005–010 реализованы и покрыты тестами.
- Для фактической проверки миграции требуется PostgreSQL 16+; в текущей среде Docker/PostgreSQL отсутствуют.
- Реализован `POST /api/v1/clients/{client_id}/submissions/import-preview`: точное позиционное распознавание v1/v2/v3, согласие, дубли, идемпотентность, шифрование и payload hash. V3 добавляет необязательный email последним, 77-м столбцом экспорта Google Forms.
- Реализован multipart `POST /api/v1/clients/{client_id}/submissions/import-preview/csv` с лимитом 2 МБ и одной анкетой на запрос.
- Accept/reject и аудит выполняются одной транзакцией PostgreSQL.
- Локальный rate limiter допускает 10 попыток импорта на пользователя/клиента в минуту; перед несколькими экземплярами API его нужно заменить распределённым хранилищем.
- Шифрование чувствительных полей выполняется приложением/KMS; открытый текст в базе не хранится.
- `GET /api/v1/clients` показывает консультанту только клиентов из его активных назначений.
- В `web/` добавлен первый интерфейс: выбор клиента, multipart-загрузка одного CSV, безопасный preview и действия accept/reject.
- Локальный UI smoke test использует только `test/fixtures/consultant-ui-synthetic.csv` и `test/consultant-ui-mock-server.mjs`.
- `GET /api/v1/auth/config` отдаёт только публичные настройки SPA; секретов в ответе нет.
- `GET /api/v1/clients/{client_id}/submissions` возвращает последние безопасные метаданные анкет только при активном назначении консультанта.
- Реальный локальный OIDC-вход проверен с Auth0 EU: сервер распознаёт связанного консультанта и возвращает только назначенного синтетического клиента.
- `GET /api/v1/clients/{client_id}/submissions/{submission_id}/analysis` выдаёт только принятую анкету, только назначенному консультанту и только по явному белому списку нормализованных полей.
- При выдаче анализа AES-256-GCM envelope и payload hash проверяются повторно; каждое успешное чтение записывается в аудит.
- В выдачу анализа не входят ФИО, телефон, Telegram, сведения о согласии/направившем лице и вложения. Интерфейс показывает исходные ответы без автоматических медицинских выводов.
- Синтетический UI smoke mock поддерживает полный сценарий до открытия рабочего обзора принятой анкеты.
- `GET /api/v1/clients/{client_id}/submissions/{submission_id}/note` возвращает только внутреннюю заметку назначенному консультанту и только для принятой анкеты.
- `PATCH /api/v1/clients/{client_id}/submissions/{submission_id}/note` требует `If-Match`, шифрует текст и атомарно создаёт неизменяемую версию с аудитом.
- Внутренняя заметка не изменяет `form_submission`, не публикуется клиенту и не включается в audit/log/error payload.
- `GET/PATCH /api/v1/clients/{client_id}/submissions/{submission_id}/booking` хранит внутренний статус записи (`pending`, `scheduled`, `needs_reminder`), согласованное время и зашифрованную заметку о связи; изменения версионируются и аудируются.
- Блок записи доступен только назначенному консультанту и только для принятой анкеты; автоматические сообщения клиенту не отправляются.
- Реализован индивидуальный белковый ориентир со встроенным, физическим и ручным источником, версионированием и аудитом.
- Реализован серверный расчёт белка по проверенным карточкам продуктов: общий, растительный и животный белок, полнота, доля растительного белка и итоги по приёмам пищи.
- Интерфейс поддерживает добавление, редактирование и удаление позиций рациона, живой предварительный расчёт и сравнение с индивидуальным диапазоном.
- Симулятор порции показывает вклад продукта и новый дневной итог без изменения сохранённого рациона до явного действия консультанта.
- Реализован модуль жиров: индивидуальный диапазон, фактическое потребление, полнота жирнокислотного профиля и профессиональные сигналы.
- Клиентские объяснения белкового и жирового модулей публикуются только после одобрения консультанта; продуктовые рекомендации остаются только в профессиональном интерфейсе.
- Общая нутриентная сводка объединяет белок и жиры, не дублирует продуктовые рекомендации и показывает актуальность клиентской публикации.
