# Белковые расчёты

## Назначение

Модуль помогает консультанту определить индивидуальный ориентир белка и оценить фактический рацион за день. Он не формирует медицинских назначений и не заменяет профессиональную интерпретацию.

Система не принимает рассчитанные нутриенты от браузера. Клиент передаёт только идентификатор проверенной карточки продукта, приём пищи и массу порции, а итог повторно рассчитывается сервером.

## Текущий пользовательский сценарий

1. Консультант открывает принятую анкету назначенного ему клиента.
2. В блоке «Белковый диапазон» задаёт ориентир встроенным, физическим или ручным способом.
3. В блоке «Белок за день» выбирает приём пищи, проверенный продукт и массу порции.
4. Симулятор без сохранения показывает:
   - вклад выбранной порции;
   - предполагаемый итог за день;
   - положение относительно целевого диапазона;
   - недостающее количество до нижней границы или превышение верхней.
5. После явного добавления порция появляется в рационе. Любую строку можно исправить или удалить.
6. Интерфейс предварительно пересчитывает общий, растительный и животный белок, долю растительного белка и итоги по приёмам пищи.
7. После сохранения сервер заново выполняет расчёт, создаёт новую неизменяемую версию и возвращает канонический результат.

Предварительный расчёт в браузере нужен только для удобства. Источником истины остаётся ответ сервера.

## Расчёт фактического белка

Для каждой валидной позиции:

```text
protein_g = mass_g × protein_per_100g / 100
plant_protein_g = protein_g × plant_share_percent / 100
animal_protein_g = protein_g - plant_protein_g
```

Дневные значения равны сумме валидных строк. Доля растительного белка:

```text
plant_share_percent = plant_protein_g / total_protein_g × 100
```

Если общий белок равен нулю, доля не рассчитывается. Значения в API округляются до двух знаков после запятой.

Поддерживаемые приёмы пищи: `breakfast`, `snack_1`, `lunch`, `snack_2`, `dinner`, `bedtime`, `other`.

Масса одной позиции должна быть больше нуля и не превышать 5000 г. Один расчёт содержит не более 100 позиций.

## Полнота и неизвестные продукты

В расчёт входят только карточки со статусом `verified`. Если карточка отсутствует или перестала быть проверенной, сервер не придумывает пищевую ценность и возвращает позицию в `unresolved`.

Полнота определяется долей разрешённых строк от общего числа строк. При полноте менее 100% сравнение с целевым диапазоном получает статус `incomplete_data`.

## Сравнение с ориентиром

Статусы дневного результата:

- `target_not_set` — ориентир ещё не сохранён;
- `incomplete_data` — не все позиции удалось рассчитать;
- `below_range` — итог ниже нижней границы;
- `within_range` — итог внутри диапазона, включая его границы;
- `above_range` — итог выше верхней границы.

Доля растительного белка показывается отдельно. Текущий интерфейс использует информационную границу 50%, но высокая или низкая доля сама по себе не трактуется как медицинский вывод.

## Карточка продукта

Проверенная карточка содержит:

- каноническое название;
- белок на 100 г;
- происхождение: `plant`, `animal` или `mixed`;
- процент растительной части;
- название и необязательную ссылку на источник;
- версию карточки и статус проверки.

Для растительного продукта доля равна 100%, для животного — 0%. Смешанный продукт может иметь промежуточное значение.

## API

Все маршруты доступны только консультанту с активным назначением на клиента. Расчёт можно читать и изменять только для принятой анкеты.

### Карточки продуктов

```http
GET /api/v1/clients/{client_id}/food-products
```

Возвращает только проверенные карточки, доступные для расчёта.

### Чтение расчёта

```http
GET /api/v1/clients/{client_id}/submissions/{submission_id}/protein-intake
```

Новый расчёт возвращается с пустым массивом `items`, `summary: null` и версией 0. Существующий расчёт содержит исходные позиции, рассчитанные строки, неразрешённые позиции, сводку и время обновления. Версия также возвращается в `ETag`.

### Сохранение расчёта

```http
PATCH /api/v1/clients/{client_id}/submissions/{submission_id}/protein-intake
Content-Type: application/json
If-Match: "{version}"

{
  "items": [
    {
      "meal_key": "lunch",
      "product_card_id": "uuid",
      "mass_g": 150
    }
  ]
}
```

Для первого сохранения используется `If-Match: "0"`. Несовпадение версии возвращает конфликт `PROTEIN_INTAKE_VERSION_CONFLICT`, сохраняя локальный ввод консультанта в форме.

## Хранение и аудит

- Текущий итог хранится в `protein_intake_assessments`.
- Каждое успешное сохранение создаёт неизменяемую запись в `protein_intake_assessment_versions`.
- Подробный payload с позициями и снимками карточек шифруется сервисом приложения.
- Агрегированные числовые значения хранятся отдельно для контролируемой выборки.
- Сохранение версии и события аудита выполняется в одной транзакции PostgreSQL.
- Используется оптимистическая блокировка через `If-Match` и номер версии.

## Основные файлы

- `src/imports/protein-intake.calculator.ts` — чистый расчёт строк и итогов;
- `src/imports/protein-intake.service.ts` — авторизация, валидация, шифрование и DTO;
- `src/imports/protein-intake.repository.ts` — транзакционное хранение, версии и аудит;
- `src/imports/food-product.repository.ts` — чтение проверенных карточек;
- `src/imports/protein-intake.controller.ts` — HTTP-маршруты и `ETag`;
- `web/app.js` — редактор, предварительный расчёт и симулятор порции;
- `web/index.html`, `web/workspace.css` — структура и адаптивное оформление;
- `test/consultant-ui-mock-server.mjs` — синтетический полный UI-сценарий.

## Проверка

Перед передачей изменений выполняются:

```sh
pnpm test
pnpm build
node --check web/app.js
git diff --check
```

Текущий набор покрывает расчёт растительного и животного белка, смешанные итоги, неизвестные карточки, неверную массу, сравнение с целью, запрет доверия клиентским нутриентам, права назначения и конфликт версий. PostgreSQL-интеграционные тесты требуют доступной тестовой базы.

## Ограничения и следующие шаги

- Каталог продуктов пока должен быть предварительно заполнен и проверен вне этого интерфейса.
- Симулятор оценивает одну порцию и не сохраняет отдельную историю сценариев.
- Пока нет недельной динамики и сравнения нескольких дней.
- Не реализованы поиск, фильтрация и управление карточками продуктов.
- До работы с реальными клиентскими данными необходимы эксплуатационные меры из `DEPLOYMENT.md`, проверка миграций на PostgreSQL и независимая проверка безопасности.

Рекомендуемый следующий инкремент: управление проверенным каталогом продуктов, затем дневные снимки и недельная динамика.
