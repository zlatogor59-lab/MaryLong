# Украинский каталог продуктов

Дата аудита: 2026-09-27.

## Цель

Сделать каталог практичным для консультаций в Украине. Приоритет Украины реализуется составом каталога и понятными названиями, а не новыми полями в клиентской консультации.

## Что уже есть

- Версионируемая карточка продукта со статусами `draft`, `verified` и `retired`.
- Белки, жиры, углеводы, витамины, минералы, источник и версия данных.
- Отдельная фиксация подтверждённого обогащения.
- В расчёт попадают только проверенные карточки; отсутствующие значения не заменяются нулём.
- В дневник добавлен поиск по названию с поддержкой украинских и русских букв, апострофов и независимым от регистра сравнением.

## Границы этапа

Не добавляем в клиентский отчёт страну продажи, происхождение сырья, метод анализа клетчатки, диапазоны или уровни уверенности. Такие данные не нужны для итога консультации.

## Порядок наполнения

1. Обычные базовые продукты: крупы, хлеб, молочные продукты, яйца, мясо, рыба, бобовые, овощи, фрукты, орехи и масла.
2. Типичные украинские блюда и домашние заготовки с ясно заданной рецептурой.
3. Часто используемые упакованные продукты по данным конкретной этикетки.
4. Редкие и специализированные продукты — только после проверки первых трёх групп на реальных рационах.

## Следующий инкремент

Собрать частотный список из реальных дневников, разделить его на «уже есть / нужен общий продукт / нужна этикетка» и по этому списку расширять каталог. Отдельный массовый импорт сомнительных таблиц не планируется.

## Результат первого сверочного списка

Рабочий реестр `UA-priority-v1` содержит 58 позиций. Это стартовый список для консультаций, а не заявление о популяционной частоте потребления.

- До импорта первой очереди 39 позиций имели подходящую проверенную карточку.
- До импорта 12 позициям была нужна общая карточка.
- 6 групп упакованных продуктов нужно вносить по конкретной этикетке.
- Первоначальный аудит считал подходящими для молока 2,5% две карточки; последующая проверка показала, что карточка 1,5–2% является отдельным продуктом, а не дублем.

Первая очередь наполнения: ржаной хлеб, кефир, кисломолочный творог 5%, сметана 15%, куриное бедро без кожи, куриная печень и хек.

Повторная сверка запускается командой `pnpm food-products:audit-ua`; она ничего не изменяет в базе.

## Импорт первой очереди

27 сентября 2026 года в локальную PostgreSQL добавлены четыре проверенные карточки:

- хлеб ржаной;
- куриное бедро без кожи, тушёное;
- куриная печень, варёная/тушёная;
- хек, гриль без добавленного жира.

Повторная синхронизация идемпотентна. После уточнения правила молока аудит показывает 44 доступные позиции, 8 отсутствующих общих карточек и 6 групп, для которых нужна конкретная этикетка. Неоднозначных сопоставлений больше нет: молоко 2,5% соответствует отдельной расчётной карточке, а карточка 1,5–2% сохранена как самостоятельная.

Кефир, кисломолочный творог 5% и сметана 15% остаются заблокированными до появления подходящего источника или набора типичных украинских этикеток.

## Управление карточками: первый блок

Добавлен административный API для безопасного цикла «черновик → проверка»:

- `GET /admin/food-products` — список с фильтрами `status` и `search`;
- `GET /admin/food-products/duplicates` — группы дублей для ручного разбора;
- `GET /admin/food-products/:id` — карточка и её текущая версия в `ETag`;
- `POST /admin/food-products` — создание карточки только в статусе `draft`;
- `PATCH /admin/food-products/:id` — редактирование только черновика с обязательным `If-Match`;
- `POST /admin/food-products/:id/verify` — перевод черновика в `verified` с обязательным `If-Match`.

Операции доступны только администратору. Перед созданием, переименованием и проверкой выполняется проверка точного нормализованного дубля: учитываются регистр, лишние пробелы, пунктуация и варианты апострофа. Более свободное нечёткое слияние оставлено человеку. Для проверки карточки обязательна ссылка или иной идентификатор источника (`source_reference`). Все изменения версии и переход в `verified` атомарны и записываются в аудит. Существующие расчёты по-прежнему используют только `verified` карточки.

Веб-интерфейс автоматически переключается на экран каталога для пользователя с ролью `admin`. Экран поддерживает поиск, фильтр по статусу, создание и редактирование черновиков, просмотр проверенных карточек и подтверждение публикации. При конфликте версий введённые данные остаются в форме, а пользователь получает явное сообщение о необходимости сравнить изменения.

Добавлен экран возможных дублей. Он показывает количество нормализованных групп и сравнивает карточки по статусу, базовому составу и источнику; различающиеся строки выделяются. Из сравнения можно открыть любую карточку или запустить подтверждаемое безопасное объединение.

## Безопасное объединение дублей

Реализовано управляемое объединение внутри нормализованной группы. Основной может стать только актуальная карточка `verified`. Администратор подтверждает действие, версии обеих карточек проверяются, после чего дубль атомарно переводится в `retired` и получает `replacement_card_id` основной карточки. Операция записывается в аудит.

Зашифрованные исторические версии рационов не переписываются. При расчёте старый идентификатор архивированного дубля прозрачно разрешается через проверенную основную карточку. Это сохраняет неизменность истории и одновременно не делает старые рационы неполными. После объединения архивная карточка исключается из списка нерешённых дублей.

Браузерная проверка выполнена на синтетическом административном контуре: просмотр проверенной карточки, редактирование и сохранение черновика, увеличение версии, подтверждение публикации, сравнение дублей и мобильная компоновка. Для воспроизводимости мок-сервер поддерживает `CONSULTANT_UI_ROLE=admin`.

## Расширенное редактирование состава

В форму черновика добавлен сворачиваемый блок для минерального, витаминного и обогатительного профилей. Данные показываются без потерь при повторном открытии карточки и доступны только для редактируемых черновиков.

Сервер не принимает произвольную структуру: проверяет перечень нутриентов, единицу каждого значения, статус происхождения данных, название и версию источника. Статус `missing` требует явного `null`, поэтому отсутствие данных не превращается в нулевое содержание. Подтверждённое обогащение принимается только при непротиворечивом типе доказательства, области идентичности продукта, рынке и составе добавленных нутриентов.

Для минералов и витаминов добавлен табличный редактор: администратор выбирает статус значения, вводит количество, источник, версию и идентификатор записи. Единица измерения закреплена за нутриентом и не вводится вручную. Пустое измеренное значение не может быть сохранено как случайный ноль; поля значения и источника становятся обязательными в зависимости от выбранного статуса. JSON сохранён в дополнительном разделе для проверки и редких расширенных операций.

## Точка продолжения

JSON профиля обогащения заменён управляемой формой со статусом, основанием доказательства, областью идентичности, рынками, ограничением и таблицей добавленных нутриентов. Интерфейс не позволяет подтвердить обогащение без доказательства и хотя бы одного полностью описанного нутриента; региональная категория требует корректного ISO-кода рынка. Технический JSON формируется автоматически и доступен только для проверки.

Полная браузерная проверка выполнена на синтетической карточке: заполнены минеральный, витаминный и обогатительный профили, черновик сохранён, закрыт, повторно открыт без потерь и опубликован. После публикации все поля стали доступны только для чтения. Проверены пограничные правила формы: неизвестный статус сбрасывает доказательство и общую идентичность, подтверждённое отсутствие обогащения блокирует таблицу добавок, подтверждённое обогащение требует хотя бы один нутриент, положительное количество, источник и версию, а региональная категория — рынок в двухбуквенном ISO-формате.

Добавлен автоматизированный браузерный регрессионный сценарий `pnpm test:browser:catalog`. Он без дополнительных npm-зависимостей запускает headless Chrome или Edge, синтетический административный сервер и проверяет полный цикл карточки. Сценарий покрывает отсутствие доказательства, неверный ISO-код рынка, неполный добавленный нутриент, сохранение и повторное открытие всех трёх профилей, конфликт версии с сохранением локального ввода и публикацию с переходом формы в режим только для чтения.

В административную карточку добавлена история действий на основе существующего аудита. Новый маршрут `GET /admin/food-products/:id/history` доступен только администратору, проверяет существование карточки и возвращает не более 100 событий в обратном хронологическом порядке. Интерфейс показывает создание, изменение черновика, публикацию и архивирование дубля с датой, ролью и контролируемым кодом причины. Журнал не содержит кнопок восстановления или изменения прошлых событий. Автоматизированный браузерный сценарий проверяет появление событий после создания, внешнего изменения и публикации, а также отсутствие управляющих полей в истории.

Добавлены неизменяемые снимки версий карточки. Миграция `202609280001_food_product_card_versions` создаёт append-only таблицу, переносит текущее состояние существующих карточек как `BACKFILL` и запрещает `UPDATE` снимков на уровне PostgreSQL. Создание, изменение, публикация и архивирование дубля теперь атомарно записывают новую версию вместе с карточкой. На локальной базе миграция создала исходные снимки для всех 84 карточек; проверочная попытка изменить снимок была отклонена триггером.

История в административной карточке показывает версии в обратном порядке и вычисляет изменения между соседними снимками. Сравнение остаётся только для чтения и не передаёт полный снимок клиенту: API возвращает только метаданные версии и пары «до / после» для изменённых полей. Автоматизированный браузерный сценарий проверяет версии 1–3, изменение источника, переход статуса при публикации и отсутствие управляющих элементов.

Сравнение составных профилей сделано человекочитаемым. Сервер больше не возвращает минеральный, витаминный или обогатительный профиль как одно изменённое поле: он формирует отдельные изменения для каждого нутриента. Статус, доказательство, область, рынки и ограничение обогащения также сравниваются раздельно. Интерфейс показывает название нутриента, статус значения, количество с единицей, источник, версию и идентификатор записи; для добавленного нутриента отдельно показывает подтверждённое количество на 100 г. Сырой JSON в истории не отображается.

Серверный тест проверяет раздельные изменения кальция, железа, витамина D и добавленного витамина D. Браузерная регрессия меняет кальций и добавленный витамин D между версиями, проверяет русские подписи и отсутствие JSON-фрагментов в интерфейсе.

Добавлена интеграционная проверка PostgreSQL `food-product-card-versions.database.spec.ts`. При `RUN_DB_TESTS=true` она подтверждает атомарность пары «карточка + снимок»: создание формирует ровно одну версию, из двух конкурирующих изменений проходит только одно и формирует ровно второй снимок, а последующий конфликт устаревшей версии не оставляет лишних записей. Проверка публикации создаёт третий снимок, а прямая попытка изменить историческую запись отклоняется триггером неизменяемости. В обычном тестовом прогоне сценарий штатно пропускается, чтобы тесты не записывали данные в PostgreSQL без явного разрешения.

Снимками версий охвачены все служебные сценарии синхронизации и импорта, включая прямые записи вне административного API. Миграция `202609280002_food_product_card_version_guard` переносит гарантию на уровень PostgreSQL: вставка автоматически создаёт исходный снимок, любое обновление продвигает версию ровно на один шаг и атомарно создаёт снимок `SYNC`, а скачок или откат версии отклоняется. Административный репозиторий передаёт триггеру точный тип операции и пользователя, поэтому история сохраняет значения `CREATE`, `UPDATE`, `VERIFY` и `MERGE` без дублирования снимков.

Добавлена проверка целостности только для чтения `pnpm food-products:audit-versions`. Она проверяет наличие снимка текущей версии, непрерывность цепочки от первого сохранённого снимка и отсутствие осиротевших записей. Исторические карточки корректно начинаются с версии, существовавшей при первичном `BACKFILL`: отсутствующие до внедрения механизма состояния не реконструируются. На локальной базе проверены все 84 карточки, нарушений и осиротевших снимков нет. PostgreSQL-интеграционный тест дополнительно проверяет прямое служебное обновление, автоматический `SYNC`-снимок и отклонение недопустимого скачка версии.

Служебные синхронизации переведены на единый операторский шлюз `run-food-catalog-operation.mjs`. Все команды из `package.json` теперь работают в режиме предварительного просмотра по умолчанию; запись включается только явным `--apply`. Неизвестные операции и флаги отклоняются, подключение разрешено только к локальной базе, а `.env` загружается одинаково независимо от оболочки запуска. Опасный ранее `food-products:seed-local` больше не применяет данные автоматически и на заполненной базе возвращает только структурированное сообщение о блокировке.

Шлюз нормализует одиночный и построчный JSON старых импортёров в общий отчёт с операцией, режимом, статусом, базой, предметным результатом и состоянием проверки целостности. После каждого успешного запуска с `--apply` автоматически выполняется `food-products:audit-versions`; нарушение цепочки версий завершает команду ошибкой. Идемпотентное применение синхронизации морепродуктов проверено на локальной базе: новых карточек не создано, все три существующие пропущены, аудит 84 карточек прошёл без замечаний.

Добавлен постоянный журнал применённых служебных синхронизаций `food_catalog_sync_runs`. Для каждого запуска с `--apply` сохраняются идентификатор, операция, время начала и завершения, состояния `running` / `succeeded` / `failed`, агрегированные счётчики результата, краткий итог проверки целостности и контролируемый код ошибки. Ограничения PostgreSQL не позволяют завершённой записи остаться без времени окончания или активной записи получить время окончания.

Полный вывод импортёра, названия исходных строк, параметры подключения и диагностический стек в журнал не записываются. Предварительный просмотр не создаёт запись. На локальной базе проверены успешный идемпотентный запуск и заблокированное первоначальное заполнение: первый сохранил три пропуска и успешный аудит 84 карточек, второй — только статус ошибки и код этапа.

Журнал синхронизаций показан администратору в режиме только для чтения. Защищённый маршрут `GET /admin/food-products/sync-runs` возвращает не более 50 запусков в обратной хронологии и выбирает только операцию, статус, безопасные резюме, код ошибки и время. Проверка сервиса подтверждает доступ администратора и маскирует существование маршрута для консультанта.

В административном каталоге добавлен компактный сворачиваемый список успешных, ошибочных и выполняющихся запусков. Он показывает только разрешённые счётчики, результат проверки карточек и контролируемый код ошибки. Браузерная регрессия проверяет оба завершённых статуса, 84 проверенные карточки и отсутствие кнопок, полей ввода или иных средств повторного запуска из истории.

Прерванные процессы синхронизации теперь обрабатываются отдельно от предметных ошибок. Во время применения шлюз обновляет `heartbeat_at` каждые 30 секунд. Перед следующим применением запись `running`, чей пульс старше пяти минут, атомарно переводится в `interrupted` с кодом `PROCESS_INTERRUPTED`; проверка целостности для неё явно остаётся невыполненной. Частичный индекс ускоряет поиск только активных просроченных запусков, а ограничения таблицы требуют времени завершения для нового терминального статуса.

Правило проверено на реальной PostgreSQL-записи с десятиминутной давностью: следующий идемпотентный запуск распознал её как прерванную, после чего синтетическая запись была удалена. Административный журнал визуально отличает состояние «Прервано» от «Ошибка» и показывает контролируемый код без диагностического стека. Браузерная регрессия покрывает успешный, ошибочный и прерванный статусы.

Параллельное применение синхронизаций исключено единой транзакционной advisory-блокировкой PostgreSQL. Шлюз получает её до создания записи `running` и удерживает до завершения импортёра и проверки целостности. Если блокировка занята, второй процесс сразу получает `CATALOG_SYNC_ALREADY_RUNNING`: предметный скрипт не запускается и лишняя запись журнала не создаётся. Предварительные просмотры остаются независимыми и блокировку не занимают.

Добавлен опциональный PostgreSQL-интеграционный тест `catalog-operation-lock.database.spec.mjs`. При `RUN_DB_TESTS=true` он удерживает блокировку отдельной транзакцией, подтверждает отказ конкурентного применения и неизменность числа журнальных записей, затем освобождает блокировку и проверяет успешный запуск с аудитом. Созданная тестом запись очищается. В обычном наборе тест пропускается штатно.

Добавлена единая полная проверка каталога `food-products:verify`. Перед запуском оператор обязан передать точное имя базы через подтверждающий параметр; шлюз сверяет его с `DATABASE_URL` и дополнительно запрещает нелокальный хост. Неизвестные параметры, отсутствие подтверждения и несовпадение имени останавливают сценарий до миграций и тестовых записей.

Команда последовательно применяет миграции, собирает сервер, запускает обычный набор тестов, отдельно включает PostgreSQL-проверки атомарности снимков и глобальной блокировки, выполняет аудит цепочек версий и реальную браузерную регрессию. Первый полный прогон на локальной базе завершился успешно: 560 обычных тестов пройдены, 7 DB-зависимых тестов штатно пропущены в обычной фазе, обе целевые PostgreSQL-проверки прошли, все 84 карточки целостны, браузерный сценарий успешен.

Полная проверка теперь формирует компактный долговечный отчёт `.artifacts/food-catalog-verification.json`. Каталог отчётов исключён из Git. Схема первой версии содержит общий статус и код, подтверждённое имя локальной базы, общую длительность, упавший этап и по каждому этапу — статус, длительность и код завершения. Вывод команд, адрес подключения, тестовые данные и диагностические стеки в файл не попадают.

Для конфигурации, миграций, сборки, обычных тестов, PostgreSQL-проверок, аудита версий и браузерного сценария закреплены отдельные стабильные коды процесса. Проверены оба исхода: неверное подтверждение базы создало безопасный отчёт `FAILED_CONFIGURATION` и завершилось кодом 2 без стека; затем полный успешный прогон восстановил итоговый отчёт `PASSED`. Последний прогон прошёл все шесть этапов примерно за 28 секунд, включая 561 обычный тест и две PostgreSQL-проверки.

Полная проверка подключена к GitHub Actions в workflow `Food catalog verification`. Для каждого push, pull request и ручного запуска он использует Node.js 22, фиксированную версию pnpm и отдельный PostgreSQL 16 с базой `consultant_catalog_ci`. Затем устанавливает зависимости с замороженным lock-файлом и вызывает ту же единую команду с точным подтверждением имени тестовой базы.

Права workflow ограничены чтением содержимого репозитория, параллельные устаревшие прогоны одной ветки отменяются, а весь job ограничен двадцатью минутами. Шаг публикации выполняется всегда и сохраняет компактный JSON-отчёт как GitHub artifact на 30 дней, включая случай падения одного из проверочных этапов. Локальный эквивалент workflow повторно прошёл все шесть этапов; облачный запуск станет доступен после отправки коммита в GitHub.

Первый реальный GitHub Actions-прогон выполнен после отправки изменений в `main`. Проверка на чистом Linux-агенте последовательно выявила и устранила три скрытые зависимости локального окружения: Prisma Client теперь явно генерируется после установки пакетов, исходные JSON каталога хранятся в отслеживаемом каталоге `data/food-catalog`, а PostgreSQL-тест глобальной блокировки самостоятельно создаёт и удаляет необходимого администратора и новые карточки. Для браузерного этапа явно задан системный Chrome.

Итоговый облачный прогон завершился со статусом `Success` примерно за одну минуту. Все этапы единой проверки прошли, а компактный отчёт `food-catalog-verification-1` опубликован как GitHub artifact. Предыдущие неуспешные попытки также подтвердили, что отчёт публикуется при падении проверочного этапа.

`main` защищена активным GitHub ruleset `Protect main with verified CI`. Изменения принимаются только через pull request после успешной проверки `verify`; обязательных сторонних одобрений нет, удаление и force push запрещены, обходной список пуст. Дальнейшая разработка ведётся в отдельных ветках.

После завершения каталога добавлена основа дневной динамики: назначенный консультант может один раз зафиксировать текущую версию подтверждённого рациона на конкретную прошедшую или текущую дату. Снимок хранит зашифрованное содержимое, версию исходного расчёта и контрольные белковые итоги; списочный API возвращает только безопасные метаданные и агрегаты. Повтор даты или версии отклоняется, а PostgreSQL запрещает изменение и удаление снимков. Создание записывается в аудит.
